数据访问发生在业务Service访问数据库的过程中，属于系统的数据访问和缓存层

在一个小的system中，我们可以将service逻辑直接连接数据库。但是在一个大型的system中，我们需要在数据库前面加入Cache。Cache解决的是如果有一段数据经常被访问，那么它们就应该存储在Cache中，来避免遍历数据库这种十分昂贵的操作。

但是这就引出了一些新的问题：

- 缓存中没有数据时，谁去查询数据库并写入缓存
- 数据库更新后，缓存怎么办

接下来，我们先了解最基本的问题：怎么管理缓存

### Cache Aside

Cache Aside 旁路缓存，应用负责同时访问缓存和数据库，并管理两者之间的数据加载。缓存位于应用访问数据库的旁边，而不是数据库请求必然经过的透明中间层

一个简化流程：

```py
① 应用查询 Redis

② 如果命中
   → 直接返回缓存数据

③ 如果未命中
   → 查询数据库
   → 将结果写入 Redis
   → 返回结果

def get_user(user_id):
    user = redis.get(f"user:{user_id}")

    if user is not None:
        return user

    user = database.get_user(user_id)

    if user is not None:
        redis.set(f"user:{user_id}", user, ttl=300)

    return user
```

更新时需要更改数据库，然后删除对应缓存。这样在下次读取的时候，其就可以从数据库拿到最新数据来更新缓存了

### write Through

这是另外一种写入策略，在写入时同时更新存储和缓存，而不是只更新数据库后删除缓存：

```py
应用写入
   ↓
缓存层 / 写入逻辑
   ├──→ 数据库
   └──→ 更新缓存
```

### 缓存穿透，击穿，雪崩

接下来我们需要看缓存存在的三个问题：

- 缓存穿透

  假设用户查询 user\_id = 99999，但是这个用户既不在缓存也不在数据库。如果应用没有缓存查不到的结果，下一次请求会重复相同过程。导致大量此类请求会不断落到数据库 → 缓存穿透

  - Solution：
    - 缓存空结果：数据库确认不存在以后，短时间缓存一个特殊值：
      ```py
      user:999999 → NOT_FOUND
      ```

      但是如果用户后来被创建，空结果会存在一段时间的过期，需要通过别的操作来避免这个事情

- 缓存击穿

  假设热门用户user123原本在缓存中，在某一个时刻这个缓存过期了。恰好有大量请求同时查询它。数据在数据库中是存在的，但是大量请求在缓存重建之前同时穿过缓存，到数据库查询同一个热点数据

  - Solution：
    - 请求合并/互斥重建：让一个请求负责查询数据库并重建缓存，其他请求等待
- 缓存雪崩

  雪崩的范围往往比击穿大，大量key或整个缓存层同时失效：

  大量缓存设置了相同的过期时间

  - Solution：

    不要让大量key在同一时刻过期

    限制回源流量，当缓存故障或大量key失效时，不要让所有请求无限制的直接到数据库
