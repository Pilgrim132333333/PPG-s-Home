worker是真正实现业务逻辑的人，其往往进行的操作是耗时的。为了增加系统的性能，我们需要将worker变得相对独立，从系统中解耦。

worker的实现有很多种，现在我们专注的是如何将请求发送到worker一侧：

```py
Client
   ↓
Nginx / 负载均衡
   ↓
订单服务
   ├──→ 数据库：保存订单
   │
   └──→ 消息队列：发送“订单已创建”消息
                    ↓
                 后台 Worker
                    ↓
                 发送确认邮件
```

当宏观上的backend收到请求的时候，其会交给特定的handler处理。如果handler直接开始业务逻辑，那么其大概率会堵塞系统。为了不堵塞系统，还能和worker通信，并且：当一个请求包含不需要立刻完成的工作时， 如何把这些交给后台（worker）处理，并在失败或重复执行的时候保证结果可靠。

### 异步操作

这是为了防止系统堵塞的核心。其允许在一个操作等待执行完毕的时候挂起，系统继续执行别的操作。这样，我们可以保证系统整体的利用率最高

### 消息队列

当服务返回值和，如何把这件事交给worker呢？答案就是消息队列。举个例子：

```py
订单服务 → 消息队列 → 邮件 Worker
```

消息队列涉及到三个主要角色：

- Producer：生产者，将service压入消息队列
- Broker：消息系统，接收、保存和分发消息的软件或服务。常见的包括RabbitMQ，Kafka
- Consumer： 消化service的一方

消息，是消息队列中的基本单位，其的样子可能是：

```py
{
  "event_id": "evt-001",
  "event_type": "order.created",
  "order_id": "order-123",
  "user_id": "user-456"
}
```

### Problem

需要注意的是，这里面的操作大多都不是原子的，这样就会导致一些问题：

- 重试：后台任务失败了。假如worker收到消息了，但是worker要执行service超时了：

  如果直接丢弃消息，那么用户可能会因为这个发生重大问题。所以我们需要重试：

  ```py
  第 1 次发送 → 失败
  等待一段时间
  第 2 次发送 → 失败
  等待更久
  第 3 次发送 → 成功
  ```

  其适合处理一些暂时性故障：网络暂时中断，下游服务暂时过载，请求超时

- 确认机制：当worker已经收到消息，但是其没有及时将完成的消息返回给队列（worker在执行完立马崩溃），那么消息队列就会重复将消息推送给worker
- 幂等：同一个业务操作被重复执行时，不会产生重复的业务效果

  返回上一个确认机制，假如重复推送给worker消息，而消息的操作是退回100元钱，如果不加入一些限制，其就会导致多一倍的损失

  - Solution：为一个业务操作分配稳定的唯一ID
    ```py
    {
      "event_id": "evt-001",
      "user_id": "user-456",
      "points": 100
    }
    ```

    之后可以通过这个ID查询是否正常执行操作

- 死信队列

  有的操作可能重试可以解决问题，但是如果遇到密码不对等问题，重试并不能解决问题。其就需要推送到死信队列。而推送时机可以设置为达到重试次数上限：

  ```py
  消息处理失败
     ↓
  按照策略重试
     ↓
  达到重试上限，或被判断为不可重试
     ↓
  进入死信队列 DLQ
  ```

基于上述过程，我们可以简化出一个简单的流程：

```py
① Client 发送创建订单请求
           ↓
② 订单服务保存订单
   并可靠地记录待发布事件
           ↓
③ 订单服务返回“订单创建成功”
           ↓
④ 事件被发布到消息系统
           ↓
⑤ 邮件 Worker 收到事件
           ↓
⑥ Worker 尝试发送邮件
     ├── 成功
     │    ↓
     │  确认消息
     │
     └── 失败
          ↓
       根据策略重试
          ├── 成功 → 确认消息
          └── 持续失败 → 死信队列
```
