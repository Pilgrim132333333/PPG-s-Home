面对一个庞大的系统，我常常不知道从哪里下手。这次尝试从零开始，把其中的设计动机拆开来看。先建立一张基础地图：一个请求如何到达服务、如何被并发处理、怎样衡量性能，以及数据如何可靠地保存和访问。

## 一、请求如何到达服务

### HTTP：描述请求与响应

HTTP 是应用层协议，规定客户端与服务器如何表示请求和响应。以推理接口为例：

```http
POST /v1/completions HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer xxx

{"prompt":"Hello","max_tokens":8}
```

请求由方法（`GET`、`POST`、`PUT`、`DELETE` 等）、资源 URL、Headers 和 Body 组成。响应会给出状态码，例如 `200 OK`，并可能带有返回数据。

| 状态码 | 含义 | 例子 |
| --- | --- | --- |
| `2xx` | 成功 | `200 OK`、`201 Created` |
| `3xx` | 重定向 | `301`、`302` |
| `4xx` | 客户端请求问题 | `400`、`401`、`403`、`404`、`429` |
| `5xx` | 服务端或上游问题 | `500`、`502`、`503`、`504` |

其中，`400` 是请求格式错误，`401` 是缺少有效认证，`403` 是没有权限，`429` 是触发限流；`502` 表示网关收到无效上游响应，`503` 表示服务暂时不可用，`504` 表示网关等待上游超时。这些状态码能帮助我们判断问题发生在哪一层。

### TCP：可靠的字节流

HTTP 描述消息，TCP 则提供可靠、按序传输字节的连接。它具备重传、流量控制和拥塞控制。建立 TCP 连接通常经过三次握手：客户端发送 `SYN`，服务端返回 `SYN+ACK`，客户端再发送 `ACK`。往返时间叫 RTT；新建连接会付出网络往返开销，所以常用持久连接复用已有连接。

TCP 为字节编号并通过 ACK 确认接收；丢失的数据会被重传。它提供的是连续字节流，没有“这是一条 HTTP 消息”的边界。应用层协议必须自行划定消息边界，例如通过长度、分隔符或其他帧格式。

```text
HTTP message → bytes → TCP segments → IP packets
```

流量控制关心接收端能否跟上，拥塞控制关心网络路径是否过载。一个 TCP 连接由源 IP、源端口、目标 IP、目标端口四元组标识，例如 `192.168.1.5:53124 → 10.0.0.8:8000`。

### DNS：从域名找到入口

访问域名时，网络最终需要 IP 地址。DNS 通过多级查询与缓存完成解析：

```text
应用 → 浏览器/操作系统缓存 → 递归解析器
     → 根 DNS → 顶级域 DNS → 权威 DNS → IP
```

DNS 记录的 TTL 是缓存有效期。TTL 较长能减少查询，但切换地址生效较慢；TTL 较短让变更更快传播，但查询量更高。

### 代理与负载均衡：入口后面的分发

正向代理代表客户端访问外部服务；反向代理代表后端服务接收客户端请求：

```text
客户端 → 正向代理 → 外部服务器
客户端 → 反向代理 → 后端服务器
```

Nginx 等反向代理可承担请求路由、TLS 终止、限流、认证、压缩、缓存、超时、重试和日志等职责。TLS 为通信提供加密、身份认证与完整性保护。一种部署方式是让代理处理 HTTPS，后端接收内部 HTTP 流量：

```text
Client --HTTPS--> Nginx --HTTP--> Backend
```

负载均衡把请求分配给多个后端。L4 负载均衡主要依据传输层信息（例如连接四元组）；L7 可以读取 HTTP 路径等应用层信息，因此能做更细的路由：

```text
/v1/chat/completions → GPU inference pool
/health              → control service
/admin               → internal service
```

常见策略有轮询、加权轮询、最少连接、最少请求和一致性哈希。选择策略要看后端处理时间是否均匀，以及请求是否需要稳定落到同一节点。Sticky Session 可以让用户回到原后端，但节点故障时会暴露状态依赖；更通用的做法是把共享状态放到 Redis 或数据库等外部系统。

## 二、请求如何被并发执行

### 进程、线程与协程

这三个概念处在不同层次：进程提供资源隔离，线程是操作系统调度执行的单位，协程是程序在用户态管理的并发任务。

```text
操作系统
└── 进程 Process
    ├── 线程 Thread 1
    ├── 线程 Thread 2
    └── 线程 Thread 3
         ├── 协程 Coroutine A
         └── 协程 Coroutine B
```

进程拥有虚拟地址空间及文件描述符等资源。多进程服务可以把 Worker 隔离开，一个 Worker 崩溃时，其他 Worker 仍可能继续工作；代价是跨进程通信和数据共享更复杂。

同一进程的线程共享内存，因此交换数据容易，但并发修改共享状态会产生竞态条件。锁可以保护临界区，保证某段共享数据在同一时刻只由符合规则的线程访问。

在 Python `asyncio` 中，调用 `async` 函数会得到协程对象，其中保存执行位置、局部变量和等待状态。`asyncio.create_task()` 把协程包装为可由事件循环调度的 Task；`asyncio.run()` 创建并运行事件循环，直到顶层协程完成。事件循环在任务遇到 `await` 主动让出控制权后切换任务。

```python
task = asyncio.create_task(fetch_data())

while True:
    ready_io = wait_for_io()
    ready_tasks = get_ready_tasks(ready_io)
    for task in ready_tasks:
        task.run_until_next_await()
```

上面的循环只是概念示意。协程的优势在于等待 I/O 时让其他任务继续运行；它本身不等于多核并行执行。

## 三、怎样衡量系统性能

延迟是一个请求从开始到完成的时间；吞吐量是单位时间完成的请求或工作量；并发量是系统中尚未完成的请求数。

平均延迟可能掩盖慢请求，所以还要看分位数：`p50` 表示 50% 的请求不超过该延迟，`p90` 表示 90% 不超过该延迟。在一个依赖多个下游的请求里，慢的分支常常决定最终等待时间，因此尾延迟很重要。

推理服务还有更贴近用户体验的指标：TTFT（发起请求到首个 Token 的时间）、TPOT（首个 Token 之后每个输出 Token 的平均时间）和 ITL（相邻输出 Token 的间隔）。

Little’s Law 将三个量联系起来：

```text
平均并发量 = 吞吐量 × 平均响应时间
```

例如系统稳定地每秒完成 100 个请求，平均响应时间为 0.2 秒，那么平均约有 20 个请求在系统中。这个关系需要在稳定状态和一致的统计口径下使用。

## 四、数据如何保存与加速访问

### 索引与事务

索引帮助数据库快速定位记录，但也会增加维护和写入成本。事务则把一组操作作为一个整体。例如转账时，扣款和入账必须共同成功或共同失败：

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE name = 'A';
UPDATE accounts SET balance = balance + 100 WHERE name = 'B';
COMMIT;
```

中途出错时可以 `ROLLBACK`。事务的 ACID 分别是原子性、一致性、隔离性和持久性。

### 隔离级别与并发异常

多个事务并发时，可能出现脏读（读到未提交数据）、不可重复读（同一事务两次读同一行结果不同）和幻读（同样条件两次查询得到不同的记录集合）。标准 SQL 隔离级别的典型关系是：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| Read Uncommitted | 可能 | 可能 | 可能 |
| Read Committed | 不允许 | 可能 | 可能 |
| Repeatable Read | 不允许 | 不允许 | 标准上仍可能 |
| Serializable | 不允许 | 不允许 | 不允许 |

实际数据库的实现可能比标准表格更复杂，分析问题时还需要看具体引擎与并发控制机制。

### 日志与缓存

数据库常用 WAL（Write-Ahead Logging）：先持久化相关日志，再允许对应数据页写入持久存储。Redo Log 支持重做已提交的变化，Undo Log 记录回退所需的信息；具体职责依数据库实现而异。

缓存用内存访问换取更低的读取延迟。数据库的 Buffer Pool 缓存数据页；Redis 等外部系统则可缓存热点业务数据。缓存引入一致性问题：数据库已经更新，缓存却可能仍是旧值。Cache-Aside 的常见流程是：

```text
读取：先查缓存 → 未命中则查数据库 → 回填缓存
更新：先更新数据库 → 再删除对应缓存
```

删除缓存与更新数据库之间仍存在并发窗口，具体方案应根据能容忍的过期时间和业务一致性要求设计。

## 写在最后

这张基础地图把系统设计串成四个问题：请求从 DNS、代理和网络协议进入；由进程、线程或协程执行；用延迟、吞吐量和并发量衡量；最后落到数据库与缓存。后续读大型系统时，我会沿着这条链路继续追问每个设计选择的动机。
